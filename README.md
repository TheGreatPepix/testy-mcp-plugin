# TestY MCP Server

MCP-сервер (Model Context Protocol) для [TestY](https://gitlab-pub.yadro.com/testy/testy) — системы управления
тестированием. Он даёт AI-агентам доступ к проектам, тест-кейсам, наборам, тест-планам, тестам, запускам
и результатам: поиск и чтение, а при наличии прав пользователя — создание, изменение и удаление сущностей.

Совместимость подтверждена на **TestY 2.2.1**.

| Параметр | Значение |
|---|---|
| Endpoint | `https://testy.example.com/plugins/mcp/` |
| Транспорт | stateless MCP Streamable HTTP, ответы в JSON |
| Версии протокола | `2025-03-26`, `2025-06-18`, `2025-11-25`, `2026-07-28` |
| Аутентификация | пользовательский токен TestY в заголовке `Authorization` |
| Страница токенов | `https://testy.example.com/plugins/mcp/tokens/` |

## Возможности

Сервер публикует семь инструментов:

| Инструмент | Назначение |
|---|---|
| `testy_list` | Список и поиск сущностей с фильтрами и пагинацией |
| `testy_get` | Получение сущности по ID |
| `testy_create` | Создание через штатный API serializer |
| `testy_update` | Частичное или полное изменение |
| `testy_delete` | Архивирование; окончательное удаление только по точной фразе пользователя |
| `testy_action` | Вызов detail-action: `ancestors`, `descendants-tree`, `progress`, `archive` и т. п. |
| `testy_api_request` | Доступ к остальным маршрутам, строго внутри `/api/v2/` |

Поддерживаются коллекции `projects`, `cases`, `suites`, `test_plans`,
`tests`, `results`, `statuses`, `test_runs`, `labels`,
`custom_attributes`, `users` и `comments`.

## Как это работает

Плагин работает внутри Django-процесса TestY и направляет каждый MCP-вызов в его внутренний DRF API v2,
не создавая второго API поверх моделей. Благодаря этому автоматически действуют:

- штатная аутентификация TestY — JWT, постоянные токены, сессии, Basic;
- роли и разрешения на уровне проектов и объектов;
- сериализаторы и бизнес-валидация установленной версии TestY;
- история, soft-delete, сигналы и сервисы TestY;
- API-действия конкретной установленной версии.

Сетевой loopback-запрос при этом не выполняется.

## Установка

Плагин ставится только из git-репозитория, в то же Python-окружение, в котором работает
backend TestY. Добавьте в зависимости backend (например, `requirements/prod.txt`) строку
с нужным тегом и пересоберите образ backend:

```text
testy-mcp-plugin @ git+https://github.com/TheGreatPepix/testy-mcp-plugin.git@v1.0.1
```

Миграции не нужны: собственных моделей у плагина нет. TestY обнаружит entry point `testy` при старте
и сам подключит приложение и URL.

## Подключение

### Токен

MCP использует аутентификацию TestY. Для агента удобнее выпустить отдельный долгоживущий токен
и передавать его в HTTP-заголовке:

```text
Authorization: Token <testy-token>
```

Страница токенов открывается из списка плагинов или напрямую:

```text
https://testy.example.com/plugins/mcp/tokens/
```

Страница требует обычной сессии TestY и показывает только MCP-токены текущего пользователя. Полный ключ
нового токена виден один раз — сразу после выпуска. Отозвать токен можно в любой момент там же.
Все инструменты выполняются с правами владельца токена: отдельного «суперпользователя MCP» нет.

Токен передаётся в схеме `Token`, как выпускает его TestY. Обычные JWT (`Bearer`), сессионная
и Basic-аутентификация TestY также доступны.

### Конфигурация клиента

Пример для клиента с поддержкой Streamable HTTP и произвольных заголовков:

```json
{
  "mcpServers": {
    "testy": {
      "type": "http",
      "url": "https://testy.example.com/plugins/mcp/",
      "headers": {
        "Authorization": "Token ${TESTY_MCP_TOKEN}"
      }
    }
  }
}
```

Для Claude Code тот же сервер можно хранить в проектном `.mcp.json`:

```json
{
  "mcpServers": {
    "testy": {
      "type": "http",
      "url": "https://testy.example.com/plugins/mcp/",
      "headers": {
        "Authorization": "Token ${TESTY_MCP_TOKEN}"
      }
    }
  }
}
```

### Готовые сниппеты для клиентов

Страница `https://testy.example.com/plugins/mcp/tokens/` содержит готовые конфигурации для самых
популярных клиентов и мост `mcp-remote` для остальных. Коротко:

- **Claude Code** — `claude mcp add --transport http --scope project testy <url> --header
  "Authorization: Token ${TESTY_MCP_TOKEN}"` или тот же сервер в `.mcp.json` (`"type": "http"`
  обязателен). Переменные `ANTHROPIC_*`, `NPM_TOKEN` и подобные в заголовках подставляются пустыми.
- **Claude Desktop** — Settings → Connectors → Add custom connector, заголовок в «Request headers».
  Коннектор подключается из облака Anthropic, поэтому TestY во внутренней сети подключайте через `mcp-remote`.
- **Codex** — `[mcp_servers.testy]` в `~/.codex/config.toml`: `url` и
  `env_http_headers = { "Authorization" = "TESTY_MCP_AUTH" }`, где `TESTY_MCP_AUTH=Token <token>`.
  Флаг `--bearer-token-env-var` не подходит: он отправляет схему `Bearer`.
- **Cursor** — `~/.cursor/mcp.json`: `url` и `headers` с `Token ${env:TESTY_MCP_TOKEN}`.
- **VS Code (GitHub Copilot)** — `.vscode/mcp.json`: `servers`, `"type": "http"`, токен через `${input:...}`.
- **Gemini CLI** — `gemini mcp add --transport http --header "Authorization: Token <token>" testy <url>`;
  в `settings.json` поле `httpUrl`, а не `url`.

Как работать с TestY экономно (сначала найти id, запрашивать только нужные поля, не перечитывать кейс
после записи, не удалять без подтверждения), агент узнаёт от самого сервера: правила передаются в
инструкциях MCP и в описаниях инструментов, объяснять их в промпте не нужно.

Не задавайте несколько источников `Authorization` одновременно. Не вставляйте секрет в настройки
клиента и не храните его в репозитории.

Интерактивный MCP OAuth плагин не публикует: используется заранее выпущенный пользовательский
токен TestY. В клиентах, которые по умолчанию запускают OAuth, выбирайте API key или явный HTTP-заголовок.

## Примеры вызовов

Получить доступные проекты:

```json
{
  "name": "testy_list",
  "arguments": {
    "entity": "projects",
    "query": {"page_size": 20}
  }
}
```

Найти тест-кейсы в проекте:

```json
{
  "name": "testy_list",
  "arguments": {
    "entity": "cases",
    "query": {
      "project": 7,
      "search": "авторизация",
      "page_size": 50
    }
  }
}
```

Изменить имя кейса:

```json
{
  "name": "testy_update",
  "arguments": {
    "entity": "cases",
    "id": 42,
    "data": {"name": "Авторизация с просроченным токеном"}
  }
}
```

Поля `data` совпадают с телом соответствующего TestY API v2 endpoint. Актуальную схему конкретной
установки можно посмотреть в `/api/v2/swagger/`.

## Транспорт и протокол

Endpoint реализует stateless MCP Streamable HTTP с JSON-ответами. Для MCP `2026-07-28` он
поддерживает `server/discover`, обязательные per-request `_meta` (`protocolVersion`,
`clientCapabilities`), `MCP-Protocol-Version`, `Mcp-Method` и `Mcp-Name`
без handshake. Заголовки сверяются с телом запроса; несовпадения возвращаются как `HeaderMismatch`
(`-32020`) с HTTP 400. Незнакомая версия протокола даёт `UnsupportedProtocolVersion`
(`-32022`) со списком поддерживаемых версий и HTTP 400. Малформированный modern-запрос
(нет обязательных полей `_meta`) даёт `Invalid params` (`-32602`) и HTTP 400,
а неизвестный метод — `Method not found` (`-32601`) и HTTP 404.

Методы initialize-эпохи (`initialize`, `ping`, `notifications/initialized`)
намеренно удалены из modern-протокола: для запроса с `_meta` версии `2026-07-28` они
возвращают `-32601`/HTTP 404. Для initialize-based клиентов те же методы продолжают работать
в legacy-режиме.

Поддерживаемые версии протокола: `2025-03-26`, `2025-06-18`, `2025-11-25`
и `2026-07-28`. Версия `2024-11-05` использует устаревший двухendpointный HTTP+SSE
transport и намеренно не заявляется. JSON-RPC batch принимается только в режиме `2025-03-26`;
начиная с MCP `2025-06-18` он корректно отклоняется. Сессии, GET-поток, `Mcp-Session-Id`
и `Last-Event-ID` не используются: запросы можно распределять между несколькими backend workers
без sticky sessions. `Origin` проверяется для всех HTTP-методов, невалидный `Origin`
даёт HTTP 403. Коды ошибок плагина не занимают зарезервированный диапазон MCP `-32020…-32099`
и legacy-диапазон `-32000…-32019`.

Сервер является tool-only MCP server: он объявляет только capability `tools`. Методы
`resources/list` и `prompts/list` намеренно не реализованы; корректный клиент не
вызывает capability, которую сервер не объявил.

## Настройки

Максимальный размер внутреннего API-ответа по умолчанию — 1 MiB. Его можно изменить в Django settings:

```python
TESTY_MCP_MAX_RESPONSE_BYTES = 2 * 1024 * 1024
```

Лучше не увеличивать лимит без необходимости, а использовать `page`, `page_size` и фильтры.

Размер страницы по умолчанию для `testy_list` — 25 записей. Значение можно изменить
(агенту всё равно можно передать `page_size` явно):

```python
TESTY_MCP_DEFAULT_PAGE_SIZE = 25
```

Вызовы `tools/call` по умолчанию ограничены 120 запросами в минуту на пользователя. Для
нескольких backend workers настройте общий Django cache (например, Redis). Лимит и окно можно изменить:

```python
TESTY_MCP_RATE_LIMIT_CALLS = 120
TESTY_MCP_RATE_LIMIT_WINDOW_SECONDS = 60
```

Если MCP endpoint вызывается браузерным клиентом с другого origin, добавьте точные разрешённые origins:

```python
TESTY_MCP_ALLOWED_ORIGINS = ["https://agents.example.com"]
```

При отсутствии заголовка `Origin` проверка не применяется; при его наличии разрешены только
origin самого TestY и значения из этого списка.

## Метки AI в тест-кейсах

Каждый тест-кейс, которого агент коснулся через MCP, получает лейбл:

| Действие агента | Лейбл | Маршруты |
|---|---|---|
| создал кейс | `AI-generated` | `POST /api/v2/cases/` (`testy_create`) |
| изменил кейс | `AI-edited` | `PUT`/`PATCH /api/v2/cases/<id>/` (`testy_update`), `PUT /api/v2/cases/bulk-update[-tree]/`, detail-action кейса (например, `archive`) |
| скопировал кейсы | `AI-copy` | `POST /api/v2/cases/copy/`, `bulk-copy/`, `bulk-copy-tree/`, `POST /api/v2/suites/copy/` (все кейсы внутри скопированных наборов) |

Кейс, созданный агентом, уже помечен `AI-generated`, поэтому `AI-edited` ему не добавляется.
Если лейбла с нужным именем в проекте ещё нет, TestY создаёт его сам. Метки ставятся одинаково
через типизированные инструменты и через `testy_api_request`.

Агент не может снять метки через MCP: при изменении кейса они возвращаются, даже если агент
передал собственный список `labels`. Массовое изменение лейблов принимает только
`labels_action` `add` или `delete`; `update` и `clear` отклоняются, а метки из списка
на удаление молча исключаются.

Копии и массовые изменения TestY выполняет сам, поэтому метки к ним добавляются отдельным
запросом `bulk-update` с `labels_action: "add"` сразу после основной операции. TestY
записывает его как ещё одну версию кейса. Если этот запрос не прошёл, инструмент возвращает
ошибку, где сказано, что основная операция уже выполнена и повторять её не нужно.

Имена и цвет настраиваются; пустое имя отключает соответствующую метку:

```python
TESTY_MCP_AI_LABEL_NAME = "AI-generated"
TESTY_MCP_AI_EDITED_LABEL_NAME = "AI-edited"
TESTY_MCP_AI_COPY_LABEL_NAME = "AI-copy"
TESTY_MCP_AI_LABEL_COLOR = "#7b61ff"  # необязательно
```

Цвет применяется, когда лейбл создаётся при создании или изменении одного кейса. Массовые
операции TestY принимают только имена лейблов, поэтому если лейбл впервые появится при копировании,
он будет без цвета.

В TestY изменение кейса заменяет его лейблы и вложения списками из запроса, поэтому `PATCH`
без этих полей стёр бы их. `testy_update` сначала читает кейс и подставляет текущие `labels`
и `attachments`, если агент их не передал.

## Архивирование вместо удаления

`testy_delete` по умолчанию ничего не удаляет. Проекты, кейсы, тест-планы и тесты он
архивирует через штатный `POST /api/v2/<entity>/<id>/archive/`, и их можно восстановить из архива.
Архивирование проекта или плана архивирует и их содержимое. Архивированный кейс получает метку
`AI-edited`.

Окончательно удалить объект можно, только если пользователь сам напишет точную фразу. Агент
передаёт её дословно в аргументе `confirmation`:

```text
Да, удали <имя объекта> в проекте <имя проекта>
Да, удали проект <имя проекта>
```

Сервер читает объект и его проект из TestY и сверяет фразу с их текущими именами. Регистр
учитывается. Повторные пробелы и кавычки вокруг фразы игнорируются. Если фраза не совпала,
вызов отклоняется, ничего не меняется, а в ответе указана правильная фраза. Фраза относится
только к объекту, который в ней назван, поэтому согласие на удаление одного кейса нельзя
применить к другому.

Сьюты, результаты, метки и другие сущности без архива удаляются только по такой же фразе.
Без неё `testy_delete` для них ничего не делает.

Другие пути удаления закрыты: `testy_action` и `testy_api_request` не принимают метод `DELETE`,
а окончательная очистка корзины (`.../deleted/remove/`) через MCP отклоняется.

Это защита на уровне протокола: сервер не может проверить, что фразу набрал именно
человек. Поэтому в клиенте стоит оставить ручное одобрение для инструментов с
`destructiveHint` и выдавать агенту токен пользователя с минимальной ролью.

## Безопасность

- endpoint требует аутентификацию DRF;
- внутренний gateway разрешает только маршруты `/api/v2/`;
- path traversal и query string в `path` запрещены;
- query-параметры передаются отдельно и безопасно кодируются;
- права проверяются повторно в штатном DRF viewset;
- ответы ограничены по размеру;
- входы инструментов проверяются по опубликованным JSON Schema;
- современные MCP-заголовки сверяются с полями JSON-RPC body;
- `Origin` проверяется для защиты от DNS rebinding;
- вызовы инструментов ограничиваются по частоте и журналируются без аргументов и токенов;
- `users` и `statuses` защищены от записи высокоуровневыми MCP-инструментами;
- мутации помечены MCP annotations как изменяющие или destructive;
- `testy_delete` по умолчанию архивирует, а удаляет только по точной фразе пользователя;
- `DELETE` и очистка корзины через `testy_action` и `testy_api_request` запрещены.

Reverse proxy должен ограничивать размер тела запроса, применять TLS и обычные для TestY rate limits.
Токен агента рекомендуется выдавать отдельному пользователю с минимально необходимой ролью.
